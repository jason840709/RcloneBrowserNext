# 0.5.0：傳輸統計與 NAS 比對的設計依據

本文件記錄 2026-10-20 查閱 rclone 1.75.2 原始碼、官方文件及舊版參考程式的結果。它說明選項的實際行為與限制；測試通過項目另見本版本驗證報告。

## 1. 為什麼已傳輸容量會增加，速度卻是 0？

rclone 的 JSON 統計放在每行記錄的 `stats` 物件中，包含 `bytes`、`totalBytes`、`speed`、`eta`、`elapsedTime`、`transfers` 等欄位。`eta` 無法估計時可以是 `null`。這些是結構化資料，不需要重新解析英文的 `Transferred:` 文字。官方文件亦說明 JSON 記錄採逐行輸出的格式。[1]

不過，`speed: 0` 不一定表示沒有複製檔案。rclone 1.75.2 有兩條不同的統計路徑：[2][3]

- 一般資料串流呼叫 `StatsInfo.Bytes`，更新累計容量與速度取樣。
- 伺服器端複製呼叫 `StatsInfo.BytesNoNetwork`，更新累計容量，但不把它算成一般網路速度。

macOS 本機後端的 `Copy` 會使用系統的 `CopyFile`，先嘗試 APFS 複製；無法共用資料區塊時，該系統呼叫也可以退回一般複製。這條路徑仍歸入 rclone 的伺服器端複製統計。因此，本機資料夾之間的作業可能持續增加已完成容量，卻回報 `speed: 0` 與 `eta: null`。[4][5]

這是能解釋該現象的實際程式路徑。僅憑使用者截圖，不能斷言某次作業一定使用了它；還需要該次 JSON 記錄才能確認。另在 Next 0.4.0 中，工作結束時會把速度欄位清成 0，這會讓完成後的速度也消失。

### 顯示速度的選擇

0.5.0 的設計是使用現有每秒統計中的累計容量，估算最近 60 秒完成多少容量。不足 60 秒時，以已經過的時間計算；完成後保留整次作業的平均值。這代表「處理容量的速度」，遇到 APFS 共用區塊或雲端伺服器端複製時，不等於網卡的實際流量。

不為了速度顯示停用 APFS 複製，也不另外讀取檔案、掃描目錄、計算雜湊或開新程序。估算最多保存 64 筆數值樣本，這些樣本不隨檔案數增加，也不傳送到介面。當 rclone 在某條系統複製路徑中只於單一檔案完成時回報容量，該檔案中途的細部進度仍然無法憑空得知。

剩餘時間是剩餘容量除以估算速度。列舉尚未完成時，總容量可能繼續增加，因此百分比及剩餘時間可能修正；不應為了固定分母而強制預掃全部目錄或放大待處理佇列。[6]

## 2. 電腦、NAS、雲端之間應該怎麼比對？

### 建議起點：大小與修改時間，不計算本機雜湊

選項對應 rclone 原本的大小與修改時間比對，再加上 `--local-hashes=none`。若大小及修改時間相符，略過該檔案；若修改時間不同，且兩端沒有可共用的雜湊，就重新傳送。這可以避免本機後端為了確認內容相同而讀取整個檔案。[7][8]

Finder 掛載的 SMB 資料夾以一般路徑交給 rclone 時，使用的是本機後端。讀取這種路徑的檔案內容，實際上仍需經過網路。因此，停用本機雜湊尤其適合這個情境。若使用 rclone 自己設定的 SMB 連線，它目前本來就不提供檔案雜湊；修改時間精度在後端宣告為毫秒。[9]

這項取捨依賴可靠的修改時間。內容變了，但大小與修改時間都維持相同時，可能被略過。反過來說，內容沒有變但修改時間變了，也可能重新傳送。若 NAS 的時間戳不穩定，應先檢查伺服器時間與檔案時間精度，再考慮適當的時間容許誤差，或針對該作業改成只比對大小。

停用本機雜湊也會移除這一端可供 rclone 使用的傳輸後內容雜湊校驗，不只是減少傳輸前比對。它不會停用檔案大小或傳輸協定本身的檢查，但不能宣稱仍提供完整的端對端內容雜湊驗證。[5][7][8]

| 選項 | 適合的情況 | 主要限制 |
| --- | --- | --- |
| 大小與修改時間，不計算本機雜湊 | 本機、Finder 掛載 NAS、一般每日增量備份 | 不能辨認大小與時間均未變的內容變動；僅時間變動可能重傳 |
| 一般大小與修改時間 | 兩端雜湊取得成本低，或願意多花讀取時間確認內容 | 修改時間不同時，rclone 可能讀取內容計算共同雜湊 |
| 只比對大小 | 修改時間無法可靠保留，且接受較弱的變更判斷 | 相同大小的改檔可能被略過 |
| 大小與雜湊 | 需要更仔細確認內容，或兩端已有共同的雜湊資料 | 本機／掛載 NAS 可能需完整讀取；沒有共同雜湊時可能退回大小判斷 |
| 只比對雜湊 | 後端回報大小不可靠，且兩端有共同雜湊 | 忽略大小及時間，也略過傳輸後大小驗證；沒有共同雜湊時，大小不同的既有檔案也可能被略過 |
| 只比對修改時間 | 有特別需求，且時間戳可靠 | 忽略大小會降低判斷能力；時間不同時仍可能涉及雜湊 |
| 全部重新傳送 | 明確要重建目標資料或覆寫既有內容 | 每個符合篩選的來源檔案都重新處理，成本最高 |

`--no-update-modtime` 只是限制更新目標時間戳，不能用來禁止雜湊讀取。`--ignore-checksum` 針對傳輸後校驗，也不能等同於選擇前述比對方式。[7][8]

### NAS → 雲端仍然有實際資料傳輸

如果 rclone 執行在 Mac，來源是 NAS、目標是另一個雲端服務，確定要更新的內容通常仍須經過 Mac：從 NAS 讀入，再上傳到雲端。這與「為了雜湊比對而額外讀取」是不同的事情。大小與修改時間加上停用本機雜湊，可以減少不必要的比對讀取，但不能把兩個不相容的服務變成直接互傳。[6]

支援同服務伺服器端複製的後端可以採用該能力；不應以任何預設方案保證所有 NAS／雲端組合都具備它。若希望 NAS 備份到雲端時不經過 Mac，需要讓傳輸程序在 NAS 或其他合適的主機上執行。此版沒有替使用者部署 NAS 上的執行服務。

## 3. 常用方案的取捨

「本機 → NAS」以同時傳輸 1 個檔案、同時檢查 10 個檔案為使用者指定的起點。它能降低多個檔案同時存取時的競爭，但不能保證磁碟一定連續配置，也不是所有 NAS 的最高速配置。檢查數過高對反應較慢的裝置可能適得其反。同時傳輸檔案數與單一檔案使用多少串流也是兩個不同設定。[1]

原生 SMB 後端支援隨機位置寫入，因此大檔案仍可能使用多條平行串流，即使同時傳輸檔案數是 1。此 NAS 方案另使用 `--multi-thread-streams=0`，關閉同一檔案分段並行；這不會停用 APFS／系統複製路徑。Finder 掛載後的本機對本機複製則原本就不會自動啟用多串流，除非使用者明確指定。[9][15]

三種常用方案都應明示目前來源與目標，套用比較方式、排除規則與傳輸參數，並保留操作前的預演。方案名稱不是方向偵測器；掛載路徑或自行命名的連線不一定能可靠判別它是 NAS。

Mac 常見可排除項目包括 `.DS_Store`、`._*`、`.Spotlight-V100/**`、`.Trashes/**`、`.fseventsd/**`、`.TemporaryItems/**`。不使用「排除全部隱藏檔」或泛用 `*.tmp`，以免排除專案設定或使用者資料。`.DS_Store` 是 Finder 的資料夾瀏覽資訊；`._*` AppleDouble 檔可能另含資源分支或 Mac 中繼資料，不能一概視為無內容的垃圾。需要保留這些資料時，使用者應能刪除對應排除規則。[10][11]

以上是檔案層級的備份取捨，不代表完整的 macOS 系統映像或 Time Machine 備份。

## 4. 同步的精確意思

本程式的同步使用 `rclone sync`：以來源為準，更新目標，並刪除目標中來源已經沒有的檔案。它不是雙向同步，也不會為了選取較新版本而反向修改來源。[12]

「目標與來源一致」仍受到選取範圍、篩選、略過選項，以及後端能保存的資料種類影響。預設不開啟 `--delete-excluded`，因此被排除的目標檔案通常不會跟著刪除。若另行啟用該選項，需要在說明中明示被排除檔案也可能刪除。[13]

這次依使用者指定，新的起始值為「不限刪除數」與「傳輸時刪除」。不限不代表一定刪除全部；它只是拿掉刪除數量上限。傳輸時刪除會在檢查及傳輸期間刪除多餘目標檔案，之後若傳輸失敗，已經刪除的檔案不會自動復原。[1]

## 5. 舊版參考的證據界線

原版 Rclone Browser 的 `job_widget.cpp` 使用多組正規表示式，處理不同 rclone 版本的英文統計行。使用者提供的 Rclone Browser 2 執行檔中，也可找到包含容量、速度與 ETA 的 `Transferred:` 正規表示式。這支持「它曾調整文字統計相容性」的判斷，但不能僅靠執行檔字串還原每一次修改理由與效能測試結果。[14]

2026-10-20 查詢提供的 RcloneBrowser2 GitHub 位址，API 回傳 404；本次沒有取得對應版本原始碼，也不把 404 解釋為專案確定遭刪除。Next 的修正依據是已可取得的原版源碼、附件的唯讀分析，以及 rclone 的官方實作。
